# Prelims Reflection Journal

**Course:** Application and Systems Integration  
**Student:** Gabriel B. Magat Jr.

This journal reflects on my learnings about APSI during the prelims. 

JavaScript does not only help in adding small effects to a particular page but manages the way data is processed and actions are performed behind the interface. I found the idea of using JavaScript objects, arrays, functions, and event handlers together to be quite powerful. When applied to the example of Our Places Passport app, a place can be defined as an object, while the functions like map() or filter() will allow me to see only restaurants, museums, or places to visit. Furthermore, calculations of the overall rating after both users submit are provided by the separate function as well. What I discovered is important for me is the fact that data should be stored in one place and, hence, the outputs such as filtered results and scores should be calculated based on this data. Nevertheless, I still have difficulties with understanding asynchronous JavaScript. The reason for that is that the processes involving location permission, searching for a map, uploading photos, or failures of the API can be finished at different times, thus, I need more practice in working with loading, success, empty, and error states without making the page inconsistent.

React became more understandable when I stopped seeing a component as a mere design element. The component has a behavior and gets its data via props. The Button, Status Chip, Place Card, Rating Row as well as the App Header included in wireframes can each be created as distinct React components with appropriate props instead of repeatedly used. I also realized something important about controlled form inputs: the React state has the value, and the event is responsible for updating it. Thus, it fits the multi-step Log an Experience form described in the proposal. What I find problematic is defining where the state should live. I know how to manage the local state like the review panel opened state, but when it comes to shared filter, user authentication state, and the data used by multiple routes I face difficulty in understanding where the state should be. I need to learn more about server-side rendering and client-side interactivity in Next.js.

The aspects of styling were instrumental in demonstrating the need for a design system to go beyond just providing a set of colors. One feature that was important was the use of custom CSS properties, which allow using one token name to control colors, spacing, border radius, and fonts of multiple elements. The design system defined certain design principles based on the five-color palette, Poppins font, four-pixel spacing values, and responsive breakpoints. For example, Flexbox is appropriate for use in cards and navigation, while Grid is most useful for creating layout for cards on a page. The accessibility specifications also changed my view on styling to account for the need to use both an icon and text for a status, avoid losing focus by having it present during the navigation, and provide good touch targets on mobile devices. Besides, I am continuing to practice responsive design, especially creating a mobile version of a desktop map and results page rather than simply scaling down everything.

The insights gained from these lessons directly impacted the development of the three documents. The proposal breaks the product down into Discover Map, Experience Feed, Place Detail, Log an Experience, and Our Passport with a clearly defined data and state for each route. The wireframes turned those routes into reusable interface patterns, separating them from unrelated pages. The design system provided shared tokens, breakpoints, and accessibility guidelines for those patterns. My next undertaking is to bridge the three concepts into code: establish the data; create separate components, and align the design with the requirements.
